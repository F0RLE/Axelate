# СТАНДАРТЫ И ТРЕБОВАНИЯ К КОДУ (FLUX PLATFORM ENGINEERING STANDARDS)

**Версия документа:** 2.1.0  
**Последнее обновление:** 2026-01-24  
**Статус:** ОБЯЗАТЕЛЬНЫЙ К ИСПОЛНЕНИЮ

Данный документ устанавливает жесткие инженерные стандарты для проекта Flux Platform. Любой код, нарушающий данные принципы, не допускается к слиянию (merge) и требует немедленной доработки. Мы придерживаемся философии **"Zero Broken Windows"** и **"Clean Code"**.

---

## 1. Санитизация и Политика "De-AI" (ZERO TOLERANCE)

**Наш код должен выглядеть как результат работы высококвалифицированных инженеров, а не LLM.**

### 1.1. Запрет на артефакты генерации
- Строжайше запрещены комментарии вида: `Generated by`, `AI suggestion`, `As an AI I think`, `Copilot fix`, `Here is the code`.
- Запрещены "водяные знаки" LLM в стилистике (например, избыточные комментарии очевидных вещей: `// Returns void`).

### 1.2. Профессиональная терминология
- Запрещен "разговорный" стиль в комментариях и документации.
- ❌ *Bad:* `"This thing tries to grab data"`
- ✅ *Good:* `"Attempts to retrieve payload with exponential backoff strategy"`
- ❌ *Bad:* `"Fixing the bug with user login"`
- ✅ *Good:* `"Patched race condition in authentication flow during session rehydration"`

### 1.3. Принцип "Осмысленности"
- Если код выглядит шаблонным (boilerplate), он должен быть абстрагирован.
- Если комментарий не объясняет *почему* принято такое архитектурное решение (бизнес-контекст или ограничение платформы), он подлежит удалению.

## 2. Архитектура и Принципы Проектирования

### 2.1. SOLID & GRASP
- **SRP (Single Responsibility):** Модуль отвечает за одного актора. Если класс управляет и рендерингом, и сетью — это нарушение.
- **OCP (Open/Closed):** Классы открыты для расширения, закрыты для модификации. Используй наследование и композицию.
- **LSP (Liskov Substitution):** Подтипы должны быть взаимозаменяемы с базовыми типами.
- **ISP (Interface Segregation):** Много маленьких интерфейсов лучше одного большого.
- **DIP (Dependency Inversion):** Высокоуровневые модули не должны зависеть от низкоуровневых. Оба должны зависеть от абстракций (Interfaces/Traits).

### 2.2. Управление состоянием
- **Single Source of Truth.** Избегать дублирования состояния в разных частях системы.
- **Unidirectional Data Flow.** Данные течут в одном направлении. Изменения состояния только через определённые точки.
- **Использовать `UIStateInterface`** для глобального состояния UI.

### 2.3. Изоляция побочных эффектов (Side Effects)
- Чистые функции (Pure Functions) должны быть приоритетом.
- Все I/O операции должны быть явно изолированы в сервисные слои (`services/`).
- Побочные эффекты документировать в JSDoc с тегом `@sideeffect`.

### 2.4. Event-Driven Architecture
- Использовать `EventBus` для коммуникации между модулями.
- Именование событий: `domain:action` (например: `page:change`, `module:download:complete`).
- Всегда отписываться от событий в методах cleanup/destroy.

## 4. Frontend (TypeScript / High Performance)

### 4.1. Type Safety (STRICT MODE)

**Конфигурация TypeScript:**
```json
{
  "compilerOptions": {
    "strict": true,
    "noFallthroughCasesInSwitch": true,
    "target": "ESNext",
    "module": "ESNext"
  }
}
```

**Правила:**
- ❌ **NO `any`:** Использование `any` запрещено. Использовать `unknown` с Type Guard.
- ✅ **Strict Null Checks:** Все поля, которые могут быть `null`/`undefined`, обрабатывать явно (`?.`, `??`).
- ✅ **Interfaces over Types:** Для публичных контрактов использовать `interface`.
- ✅ **Explicit Return Types:** Публичные методы должны иметь явный return type.

```typescript
// ❌ Bad
function processData(data: any) {
    return data.value;
}

// ✅ Good
function processData(data: unknown): string | null {
    if (isValidData(data)) {
        return data.value;
    }
    return null;
}

function isValidData(data: unknown): data is { value: string } {
    return typeof data === 'object' && data !== null && 'value' in data;
}
```

### 4.2. Interfaces & Types

**Naming Conventions:**
- Интерфейсы: `I` prefix для важных контрактов (`IApp`, `IModule`, `IConfigField`)
- Type aliases: без prefix, PascalCase (`LogEntry`, `ModuleDownloadState`)
- Generics: одна заглавная буква (`T`, `K`, `V`) или описательное имя (`TPayload`)

```typescript
// ✅ Хорошо определённый интерфейс
export interface IApp {
    id: string;
    name?: string;
    nameKey?: string;
    desc?: string;
    descKey?: string;
    icon?: string;
    type?: 'api' | 'local';
    installed?: boolean;
    repoUrl?: string;
    config_schema?: Record<string, IConfigField>;
}
```

### 4.3. Performance & Lifecycle

**DOM Manipulation:**
- Прямой доступ к DOM (`document.getElementById`) минимизировать. Кэшировать ссылки.
- Использовать `requestAnimationFrame` для анимаций.
- ❌ Никогда не использовать `setInterval` для визуальных эффектов.

**Memory Management:**
- **ОБЯЗАТЕЛЬНО:** Все подписки (`addEventListener`, `Observer`, `WebSocket`, `EventBus.on`) удалять в методах очистки.
- Утечка памяти — это **блокирующий баг P0**.
- Использовать `debounce`/`throttle` для обработчиков `onInput`, `onResize`, `onScroll`.

```typescript
// ✅ Правильная очистка
class ModuleUI {
    private unsubscribers: (() => void)[] = [];

    public init(): void {
        const unsub = eventBus.on('page:change', this.handlePageChange);
        this.unsubscribers.push(unsub);
        
        window.addEventListener('resize', this.handleResize);
        this.unsubscribers.push(() => window.removeEventListener('resize', this.handleResize));
    }

    public destroy(): void {
        this.unsubscribers.forEach(fn => fn());
        this.unsubscribers = [];
    }
}
```

### 4.4. Security

- **XSS Prevention:** Запрещен `innerHTML` для пользовательского контента. Использовать `DOMPurify.sanitize()` или `textContent`.
- **No Sensitive Data:** Никаких API-ключей, секретов на клиенте. Использовать `fluxAPI.secureStorage`.
- **CSP Compliance:** Никаких inline scripts. Все скрипты через модули.

```typescript
// ✅ Безопасная вставка контента
import DOMPurify from 'dompurify';

const sanitizedHtml = DOMPurify.sanitize(userInput);
element.innerHTML = sanitizedHtml;

// Или ещё лучше:
element.textContent = userInput;
```

### 4.5. Async/Await Best Practices

```typescript
// ❌ Bad: Unhandled promise
async function loadData() {
    const data = await fetchData();
    return data;
}
loadData(); // Promise ignored!

// ✅ Good: Proper error handling
async function loadData(): Promise<Data | null> {
    try {
        const data = await fetchData();
        return data;
    } catch (error) {
        console.error('[Module] Failed to load data:', error);
        globalThis.showToast?.('Failed to load data', 'error');
        return null;
    }
}

// ✅ Good: Top-level await or .catch()
loadData().catch(console.error);
```

## 5. Backend (Rust / Safety & Concurrency)

### 5.1. Error Handling (Panic-free zone)

- **Result Propagation:** Функции возвращают `Result<T, E>`, а не паниковать.
- **Structured Errors:** Использовать `thiserror` для библиотек, `anyhow` для приложений.

**Unwrap Policy:**
- `unwrap()` / `expect()` разрешены ТОЛЬКО:
  1. В тестах (`#[cfg(test)]`)
  2. В `const` инициализации или `lazy_static`/`once_cell`
  3. Когда инвариант доказан математически (с комментарием `// SAFETY: ...`)
- Во всех остальных случаях — `match` или `?`.

### 5.2. Concurrency & Async

- **Non-blocking:** Никогда не блокировать поток Tokio (`std::thread::sleep`).
- Использовать `tokio::time::sleep` или `tokio::task::spawn_blocking` для тяжёлых вычислений.
- **State Sharing:** Минимизировать `Mutex`. Рассмотреть Actor Pattern через `mpsc` каналы.

### 5.3. Code Style (Idiomatic Rust)

- Использовать Clippy как закон: `cargo clippy -- -D warnings`
- **Newtype Pattern:** Типы-обёртки вместо примитивов (`struct UserId(String)`).
- Документация через `///` для публичных API.

## 8. Testing Standards

### 8.1. Test Framework

- **Vitest** — основной фреймворк тестирования
- Конфигурация в `vite.config.ts`

### 8.2. Test Structure

```typescript
import { describe, it, expect, vi, beforeEach } from 'vitest';

describe('ComponentName', () => {
    beforeEach(() => {
        // Setup/cleanup
    });

    describe('methodName', () => {
        it('should do X when Y', () => {
            // Arrange
            const input = createTestInput();
            
            // Act
            const result = component.method(input);
            
            // Assert
            expect(result).toBe(expected);
        });

        it('should handle edge case Z', () => {
            // ...
        });
    });
});
```

### 8.3. Naming Convention for Tests

- Файлы: `ComponentName.test.ts`
- Describe: название компонента/модуля
- It: `should [expected behavior] when [condition]`

### 8.4. Mocking

```typescript
// Использовать vi.fn() для моков
const handler = vi.fn();
eventBus.on('page:change', handler);

eventBus.emit('page:change', { pageId: 'home' });

expect(handler).toHaveBeenCalledTimes(1);
expect(handler).toHaveBeenCalledWith({ pageId: 'home' });
```

### 8.5. Coverage Requirements

- Сервисы (`services/`): минимум 80% coverage
- Utility функции: 100% coverage
- UI компоненты: тестировать критическую логику

## 13. Error Handling Patterns

### 13.1. Try-Catch Boundaries

```typescript
// ✅ Обработка на границе операции
private async _handleDeleteModule(app: IApp, category: string): Promise<void> {
    console.debug('[AppUI] Remove module requested:', app.id);
    try {
        if (globalThis.__TAURI__?.core) {
            await globalThis.__TAURI__.core.invoke('delete_module', { moduleId: app.id });
            app.installed = false;
            // Update UI...
        }
    } catch (err) {
        console.error('Delete error:', err);
        this.showToast(
            globalThis.t?.('ui.launcher.web.delete_model_error', 'Delete error') ?? 'Delete error',
            'error'
        );
    }
}
```

### 13.2. Graceful Degradation

```typescript
// Проверяй доступность API перед использованием
if (globalThis.aiBridge) {
    await globalThis.aiBridge.startProvider(app.id);
} else if (globalThis.showToast) {
    globalThis.showToast('AI Bridge not initialized', 'error');
}
```

## 32. Caching Strategies

### 32.1. LocalStorage with TTL

```typescript
interface CachedData<T> {
    value: T;
    timestamp: number;
    ttl: number;  // milliseconds
}

function setWithTTL<T>(key: string, value: T, ttlMs: number): void {
    const data: CachedData<T> = {
        value,
        timestamp: Date.now(),
        ttl: ttlMs
    };
    localStorage.setItem(key, JSON.stringify(data));
}

function getWithTTL<T>(key: string): T | null {
    const raw = localStorage.getItem(key);
    if (!raw) return null;
    
    try {
        const data: CachedData<T> = JSON.parse(raw);
        const isExpired = Date.now() - data.timestamp > data.ttl;
        
        if (isExpired) {
            localStorage.removeItem(key);
            return null;
        }
        
        return data.value;
    } catch {
        return null;
    }
}
```

### 33.2. Usage Pattern

```typescript
import { FEATURE_FLAGS } from '@/config/featureFlags';

function renderChatInput(): void {
    if (FEATURE_FLAGS.ENABLE_VOICE_INPUT) {
        renderVoiceButton();
    }
    
    // Percentage-based rollout
    if (shouldEnableFeature('ENABLE_NEW_CHAT_UI')) {
        renderNewChatUI();
    } else {
        renderLegacyChatUI();
    }
}

function shouldEnableFeature(flag: FeatureFlag): boolean {
    const value = FEATURE_FLAGS[flag];
    
    if (typeof value === 'boolean') return value;
    if (typeof value === 'number') {
        // Consistent per-user rollout based on user ID hash
        const userId = localStorage.getItem('user_id') || 'anonymous';
        const hash = simpleHash(userId);
        return (hash % 100) / 100 < value;
    }
    
    return false;
}
```

### 34.2. Error Tracking Integration

```typescript
// ✅ Центральная точка для всех ошибок
class ErrorTracker {
    private static sessionId = crypto.randomUUID();
    
    static capture(
        error: Error,
        severity: ErrorSeverity,
        context: { module: string; action: string }
    ): void {
        const trackedError: TrackedError = {
            id: crypto.randomUUID(),
            message: error.message,
            stack: error.stack,
            severity,
            context: {
                ...context,
                sessionId: this.sessionId,
            },
            timestamp: Date.now(),
        };
        
        // Log locally
        errorHandler.captureError(error, context.module);
        
        // Send to backend (non-blocking)
        this.sendToBackend(trackedError).catch(() => {
            // Silent fail - don't break user experience
        });
    }
    
    private static async sendToBackend(error: TrackedError): Promise<void> {
        if (!globalThis.__TAURI__?.core) return;
        
        await globalThis.__TAURI__.core.invoke('log_error', { error });
    }
}
```

### 34.3. Performance Metrics

```typescript
// ✅ Замер критических операций
async function measureAsync<T>(
    name: string,
    operation: () => Promise<T>
): Promise<T> {
    const start = performance.now();
    
    try {
        const result = await operation();
        const duration = performance.now() - start;
        
        console.debug(`[Perf] ${name}: ${duration.toFixed(2)}ms`);
        
        // Alert if too slow
        if (duration > 1000) {
            console.warn(`[Perf] Slow operation: ${name} took ${duration}ms`);
        }
        
        return result;
    } catch (error) {
        const duration = performance.now() - start;
        console.error(`[Perf] ${name} failed after ${duration.toFixed(2)}ms`);
        throw error;
    }
}

// Usage
const modules = await measureAsync('loadModules', () => fetchModules());
```

## 35. Anti-Patterns (What NOT To Do)

### 35.1. TypeScript Anti-Patterns

```typescript
// ❌ NEVER: Type assertion to bypass checks
const data = response as any as UserData;

// ❌ NEVER: Non-null assertion without proof
const element = document.getElementById('app')!;

// ❌ NEVER: Implicit any in callbacks
array.map(item => item.value);  // If 'item' is any

// ❌ NEVER: Enum with computed values
enum Status {
    Active = getActiveCode(),  // Bad
}
```

### 35.2. Memory Leak Patterns

```typescript
// ❌ NEVER: Forgotten event listeners
element.addEventListener('click', handler);
// Missing: element.removeEventListener('click', handler);

// ❌ NEVER: Uncleared intervals
const interval = setInterval(update, 1000);
// Missing: clearInterval(interval);

// ❌ NEVER: Closure over large objects
function createHandler(largeData: HugeObject) {
    return () => {
        // largeData is captured and never released
        console.log(largeData.id);
    };
}
```

### 35.3. Security Anti-Patterns

```typescript
// ❌ NEVER: Direct innerHTML with user input
element.innerHTML = userInput;

// ❌ NEVER: eval or Function constructor
eval(userCode);
new Function(userCode)();

// ❌ NEVER: Hardcoded secrets
const API_KEY = 'sk-12345...';

// ❌ NEVER: Logging sensitive data
console.log('API Key:', apiKey);
console.log('User password:', password);
```

### 35.4. Performance Anti-Patterns

```typescript
// ❌ NEVER: Sync operations in render loop
function render() {
    const data = localStorage.getItem('huge-data');  // Sync!
    JSON.parse(data);  // Expensive!
}

// ❌ NEVER: Creating functions in loops
items.forEach(item => {
    element.addEventListener('click', () => handle(item));  // New function each time
});

// ❌ NEVER: Layout thrashing
elements.forEach(el => {
    const height = el.offsetHeight;  // Read
    el.style.height = height + 10 + 'px';  // Write
    // Next iteration: read triggers forced reflow
});
```

### 35.5. Architecture Anti-Patterns

```typescript
// ❌ NEVER: God objects
class AppManager {
    handleAuth() { }
    renderUI() { }
    fetchData() { }
    manageState() { }
    logErrors() { }
    // 50+ more methods...
}

// ❌ NEVER: Circular dependencies
// fileA.ts imports fileB.ts
// fileB.ts imports fileA.ts

// ❌ NEVER: Magic strings/numbers
if (status === 3) { }  // What is 3?
if (type === 'xyz123') { }  // What is xyz123?
```

## 36. Чистый Код и Минимализм (The Zen of Flux)

### 36.1. Политика "Нет Мертвому Коду" (Zero Tolerance)

**Мы не храним мусор.** Код должен либо работать, либо быть удален.

- **Запрещено:** Закомментированные блоки кода (если это не пример). Git помнит историю; не нужно хранить старые куски "на всякий случай".
- **Запрещено:** Неиспользуемые интерфейсы, переменные или импорты.
- **Запрещено:** Методы, которые никогда не вызываются.

```typescript
// ❌ Bad: Кладбище мертвого кода
// function oldWay() {
//    return true;
// }

// ❌ Bad: Спекулятивный интерфейс (никто его не использует)
interface IFutureFeature {
    teleport(): void;
}

// ✅ Good: Только то, что исполняется
```

### 36.2. YAGNI (You Aren't Gonna Need It)

Не реализуйте фичи, типы или абстракции "на будущее". Обновляйте стандарты когда возникнет потребность, а не заранее.

- Не создавайте `BaseManagerAbstractFactory`, если вам нужна просто функция.
- Не добавляйте поля в интерфейсы "потому что они могут пригодиться позже".

### 36.3. Лаконичность (Меньше - Лучше)

**Мы предпочитаем компактный код.** Излишняя многословность добавляет шум и усложняет чтение.

- **Минимизируйте LOC (Lines of Code).** Если логику можно выразить в 1 строку, не растягивайте её на 5.
- **Тернарные операторы приветствуются.** Используйте их для условного присваивания без временных переменных.
- **Fail fast.** Возвращайте управление рано (`return`), чтобы избежать глубокой вложенности.

```typescript
// ❌ Bad: Излишняя многословность
let status;
if (user.isActive) {
    status = 'Active';
} else {
    status = 'Inactive';
}

// ✅ Good: Лаконично
const status = user.isActive ? 'Active' : 'Inactive';
```

### 36.4. Правило Бойскаута

**"Всегда оставляй лагерь чище, чем он был до тебя."**

- Если зашли в файл поправить баг и видите опечатку в комментарии — исправьте.
- Если видите переменную `x` — переименуйте в `timeoutMs`.
- Если видите мертвый код — удалите.
- **Маленькие, постоянные улучшения предотвращают накопление техдолга.**
